# Codex-Equivalent Autonomous Coding Design

Date: 2026-11-19

## Intent

JSON_CODR will use installed local Ollama models to inspect and work on arbitrary selected Git projects through the existing durable `AgentRuntime`. The experience should match Codex's autonomy boundary: the agent may reason, inspect, search, and prepare proposals automatically, but it pauses before file mutations, command execution, network access, installations, Git commits or publication, destructive operations, and other external effects. Model output never authorizes itself.

Success means a user can submit a coding outcome, review or revise the generated plan or one step, approve exact effects, steer or stop the task, recover after restart, undo mutations, and receive verification backed by persisted evidence. Hosted-model credits are not required when a local model is selected.

## Goals

- Route the canonical Workspace task flow through `AgentRuntime` instead of the single-shot Git broker flow.
- Capture trusted project instructions and bounded source context before planning.
- Let the planner iterate through read, search, edit, test, and verification results.
- Pause at the Codex-equivalent effect boundary and bind approval to the exact proposed call and current project state.
- Preserve durable plans, step revisions, steering, cancellation, retries, checkpoints, evidence, and restart recovery.
- Support `qwen2.5-coder:7b-instruct-q4_K_M` through a separately verified structured broker route without falsely labeling it as native tool calling.
- Equip the planner with a verified, discoverable catalog covering the complete software-development lifecycle, including explicitly enabled infrastructure and deployment operations.
- Prevent implicit network access and automatic Git grants.
- Roll back or offer exact undo for every approved mutation.

## Non-goals

- Matching the reasoning quality or context capacity of hosted Codex models.
- Allowing arbitrary shell commands generated by a model.
- Automatically installing missing tools, models, or dependencies without approval.
- Automatically committing, syncing, fetching, or pushing.
- Treating a configured model name as verified without a local conformance result.
- Supporting non-Git project mutation in the first remediation release.
- Granting infrastructure or production authority merely because a connector or CLI is installed.

## Anti-goals

- Do not repair parsing by extracting the first JSON-looking substring from arbitrary prose.
- Do not use a broad persistent project grant as approval for later effects.
- Do not execute a repaired model payload under authority granted to its original payload.
- Do not mutate the user's checked-out branch speculatively and leave failed work behind.
- Do not collapse a mixed action sequence into one policy decision.

## Constraints

- Localhost-only service and local Ollama remain the default privacy boundary.
- Existing `TaskStore`, `CoreService`, `PolicyService`, `ContextService`, `ProjectAdapter`, and `AgentRuntime` remain authoritative.
- Existing Workspace request and response fields remain backward compatible where practical.
- Project paths must remain beneath the explicitly selected project root and may not traverse symlinks or Windows reparse points.
- All model-generated structures are untrusted until strict schema validation completes.
- File and command approvals are one-shot by default. Settings may allow the user to create explicit project-scoped rules, but no model can create or widen a rule.
- Repository content, project instructions, tool output, dependency metadata, browser content, connector data, and deployment logs are untrusted input. They cannot override system policy, authorize an effect, change a credential reference, or alter the active project/environment boundary.
- A model or adapter version change invalidates its conformance evidence until the exact model digest, runtime, prompt-contract version, and adapter version pass verification again.

## Approaches considered

### 1. Connect Workspace to `AgentRuntime` — selected

Reuse the durable planner/action/verifier loop and strengthen its project registration, planning, approval, rollback, and model-conformance boundaries. This concentrates policy and recovery in one canonical path and best matches Codex behavior.

### 2. Expand the Git broker into a second agent loop

This reduces initial rewiring but duplicates planning, task state, approvals, recovery, and verification. The duplicated paths would drift and create conflicting security semantics.

### 3. Delegate to Aider or Continue

This can provide strong coding behavior quickly, but JSON_CODR would not remain the authority for every plan, effect, checkpoint, and recovery decision. It is retained only as an optional explicitly approved external capability.

## Canonical task flow

1. The Workspace registers the selected resolved project root under a generated project ID.
2. It creates an accepted goal revision and a durable root `agent.run` task.
3. `AgentRuntime` captures project instructions, a bounded file inventory, and relevant source context.
4. The local planner returns exactly one typed `CapabilityCall` or declares that it is ready for verification.
5. Reads and searches run automatically and their results become context for the next planning turn.
6. File changes and commands stop at `task.permission_required`. The UI displays the exact step, target, patch or command, risk, and project fingerprint.
7. The user may approve, reject, directly edit the step, request a revision of that step, or request a revision of the whole plan.
8. Approval is one-shot and digest-bound. Any change to the proposal or project fingerprint invalidates it.
9. An approved mutation runs in an isolated worktree or through an atomic checkpoint-capable adapter. Its result and checkpoint become durable task evidence.
10. Allowlisted verification commands require their own exact approval unless a user-created project rule already covers them.
11. Verification consumes current project evidence. Completion occurs only when every goal criterion has fresh evidence.
12. Commit, fetch, sync, push, installation, arbitrary commands, and network access always form separate approval steps.

## Planning and model contracts

The planner uses Ollama structured output with `planner_output_schema()` directly. Its schema includes `done`, one capability identifier, one operation, target path, and typed arguments. The prompt contains the current goal, approved plan revision, project snapshot, prior action results, steering, and failure evidence.

JSON_CODR will distinguish:

- **Native tool models:** locally proven to emit and consume the native tool protocol.
- **Broker-verified models:** locally proven to satisfy JSON_CODR's structured planner contract.
- **Chat-only models:** allowed to generate text but not executable proposals.

`qwen2.5-coder:7b-instruct-q4_K_M` becomes broker-verified only after passing the local conformance suite. Configuration is evidence-backed rather than a static assertion. A missing configured fallback is reported and is never treated as available.

Strict compatibility normalization may remove surrounding whitespace or one exact `json` fence. It must reject prose, multiple fences, duplicate keys, unknown fields, oversized output, invalid Unicode, and multiple objects. A model-based repair is not automatically executable; if retained, it creates a new proposal digest and returns to review.

## Coding capability system

The planner does not rely on remembered shell syntax or an open-ended tool prompt. JSON_CODR publishes a versioned capability registry. Every entry declares a stable identifier, purpose, typed input and output schemas, effect class, approval requirement, platform and runtime prerequisites, supported project types, bounded examples, verification strategy, rollback strategy, and availability probe. Only probed and policy-visible entries appear in the planner schema.

The initial registry covers the full development lifecycle:

- Project discovery, instruction loading, language/framework detection, file inventory, dependency graphing, symbol lookup, references, and semantic or text search.
- Bounded file read, create, edit, rename, move, copy, and delete with path confinement, checkpoints, diffs, and undo.
- Code generation, refactoring, bug diagnosis, API/schema changes, data migrations, documentation, tests, fixtures, configuration, localization, accessibility work, performance analysis, and security review.
- Named build, test, lint, format, type-check, static-analysis, package, benchmark, and application-run profiles discovered from trusted project configuration and displayed as exact argv before approval.
- Dependency inspection, license and vulnerability review, lockfile updates, package installation, runtime installation proposals, and reproducible environment setup.
- Git status, diff, branch and worktree operations, commit, merge/rebase, fetch, sync, push, pull-request preparation, and rollback, each split into its own policy-visible effect.
- Local services, databases, containers, browser testing, API testing, desktop application testing, MCP/connectors, language servers, debuggers, profilers, and artifact creation.
- Infrastructure planning and validation for declarative systems such as Terraform, Bicep, CloudFormation, Kubernetes, Helm, Docker/Compose, and provider CLIs when their adapters are installed and verified.
- Deployment preview, staging deployment, production deployment, health checks, log inspection, rollback, and incident recovery through explicitly configured adapters.

Capabilities use adapter interfaces rather than raw model-generated commands. A missing adapter, executable, credential, runtime, project manifest, or environment configuration produces a typed unavailable result and a reviewable prerequisite proposal; it never triggers silent installation or a guessed substitute.

Project-specific capability discovery is bounded and deterministic. Trusted manifests may add named profiles, but model-written files cannot authorize themselves during the same task. Newly created or changed profiles require re-discovery and user review before execution.

Repository-provided instructions and profiles carry provenance and trust labels in planner context. They may guide coding conventions, but never supersede JSON_CODR policy. Capability descriptions presented for approval are generated from canonical validated structures, not model-authored labels, preventing misleading names from disguising an effect.

## Infrastructure and deployment boundary

Infrastructure and deployment are first-class but disabled by default. Enabling them requires a user-selected project, named environment, installed verified adapter, opaque credential reference, and an allowlisted account/subscription, region, cluster, namespace, service, and target. Credentials are never placed in prompts or event payloads.

The required progression is:

1. Read-only discovery and current-state capture.
2. Local validation and a deterministic plan, diff, or dry run.
3. User review of target identity, proposed changes, estimated blast radius, credential reference, and rollback procedure.
4. One-use approval bound to the exact plan digest and latest remote-state fingerprint.
5. Apply with streamed redacted evidence and cancellation behavior defined by the adapter.
6. Post-deployment health verification.
7. Completion only after evidence passes; otherwise a separately approved rollback proposal.

Production deployments, destructive infrastructure changes, secret rotation, DNS changes, database migrations against shared environments, and rollbacks always require explicit approval even when a project-scoped rule exists. The model cannot broaden account, region, cluster, namespace, or environment scope. Preview authority never implies apply authority, and staging authority never implies production authority.

External rollback is not represented as guaranteed. Each adapter declares whether rollback is transactional, compensating, manual, or unavailable before approval. When rollback is unavailable, the UI displays that fact as a blocking high-risk condition and requires stronger confirmation.

## Project context

`ProjectContextResolver` becomes a mutable project registry scoped to the application runtime and backed by durable project metadata. Each task resolves only its registered project ID. Context capture honors `AGENTS.md` and related project instructions, ignores secrets and binary files, bounds individual and aggregate bytes, and records omissions.

The planner may request additional reads or searches. Results are persisted as child-task events and fed into the next turn. The Workspace no longer asks a model to produce an informed patch before it has seen the relevant files.

## Plans and revision

Plans are persisted as revisions. A revision contains ordered typed steps, stable step IDs, dependency relationships, and an approval state. Users can:

- Approve or reject the whole plan.
- Directly edit the whole plan and create a new revision.
- Request a model revision of the whole plan.
- Approve, reject, directly edit, or request revision of one step.

Editing or revising invalidates approvals for the affected step and all dependent steps. Completed evidence remains historical but does not satisfy a changed goal or step revision.

## Authorization model

Policy is evaluated per `CapabilityCall`, never per batch. Default behavior is:

- Automatic: reasoning, context assembly, project inventory, bounded read, bounded search, task state operations.
- Approval required: file creation/edit/move/delete; checkpoints restored into the project; test, lint, build, or other command execution; browser control; connectors; network access; installations; Git commit/fetch/sync/push; destructive effects.
- Explicit approval with a configured adapter and target: infrastructure apply/change/destroy, shared database migration, staging or production deployment, secret or DNS change, and rollback.
- Denied: path escape, symlink/reparse traversal, unregistered project, opaque arbitrary shell proposed as a structured project operation, privacy/cost boundary mismatch, stale proposal, or unsupported capability.

An approval record contains the principal, project ID, root digest, task and step revision, canonical call digest, project fingerprint, scope, expiry, and one-use state. Persistent project rules are user-created settings objects with an allowlisted capability and operation; they cannot contain arbitrary command wildcards.

Approval presentation is derived from the same canonical payload whose digest is authorized. The UI displays resolved target paths, exact argv, network destinations, account/environment identities, credential-reference labels, mutation summaries, and rollback class. Model-authored prose is visually separated and cannot replace canonical fields. Approval consumption is atomic; concurrent tasks cannot reuse it.

The policy store distinguishes proposal, approval, and execution principals. Adapters receive only execution authority and cannot mint approvals. Revocation, rejection, edit, model repair, plan revision, project change, environment change, credential rotation, server restart for ephemeral approvals, or expiration invalidates authority.

## Mutation isolation and recovery

Preferred execution uses a temporary Git worktree rooted under JSON_CODR's managed data directory. The approved patch applies there, verification runs there, and the resulting diff is shown before any merge into the user's branch. Applying the verified diff to the selected branch is a separate approved file-change effect with a pre-apply checkpoint.

When worktree isolation is unavailable, `ProjectAdapter` atomic checkpoints are mandatory before each target mutation. A failed patch, cancelled task, failed verification, or process interruption leaves a recoverable checkpoint and never silently reports completion. Undo restores the exact prior bytes, including deletion of newly created files.

No broker operation performs an implicit fetch. Network operations are explicit calls.

Project mutation uses a per-project writer lock and optimistic fingerprint check. Multiple read-only tasks may coexist; only one mutation may cross the approval-to-apply boundary at a time. Worktree paths, checkpoint storage, and temporary files live under a managed root with restrictive permissions and are reconciled after interruption.

## Commands and verification

Models cannot provide raw command strings. They select a named verification profile from a project-visible allowlist. The UI resolves the exact argv and working directory before approval. A user may also approve a manually entered exact command through the existing terminal proposal system; that authority does not transfer to the model planner.

Verification evidence records the command profile, argv digest, exit status, bounded output digest, project fingerprint, and observation time. A passing action event alone is insufficient when a criterion requires a command or artifact.

Approval does not make an untrusted command safe. Commands run through a constrained execution adapter with an explicit working directory, sanitized environment, secret-free prompt context, bounded runtime/output/process count, cancellation, and network disabled unless separately approved. Filesystem access is limited to the isolated worktree and explicitly mounted tool caches when the platform sandbox supports it. If an equivalent sandbox is unavailable, the UI identifies the reduced isolation before approval and production/deployment execution is denied by default.

Command and tool output is treated as untrusted data. Terminal escape sequences are stripped or safely rendered, URLs are inert until approved, output cannot generate approvals, and redaction occurs before persistence or display.

## Secrets and data boundaries

Default context collection excludes known secret files, credential stores, private keys, environment files, cloud profiles, browser profiles, and files rejected by binary/size policy. A user may explicitly attach sensitive local content, but its sensitivity label propagates through context, events, artifacts, and export rules.

Credential values are resolved only inside the executing adapter from opaque references after approval. They never enter model prompts, plans, logs, task events, command previews, checkpoints, diagnostics, or exported bundles. External inference or connector routes require a separate data-boundary approval that lists the exact data classes leaving the machine.

Persisted audit events are append-only and hash-linked through the existing task event chain. High-risk effects record canonical proposal, approval, executor identity, target identity, adapter/model digests, timestamps, evidence digests, and redacted outcome. Audit and checkpoint retention are bounded and user-manageable without weakening active recovery.

## API and UI behavior

`POST /api/workspace/tasks` creates the durable root task and returns running or approval-required state rather than executing a single broker response to completion. Task event polling/streaming supplies plans, steps, approvals, activity, checkpoints, evidence, and completion.

The existing core task endpoints remain canonical for steer, cancel, retry, approve, and resume. Workspace-specific endpoints may adapt these contracts but do not bypass them. The UI clearly identifies requested and effective models and whether the route is native, broker-verified, or chat-only.

## Failure handling

- Invalid model output creates a safe planner failure event and may retry within a bounded planner budget.
- Repeated identical failed calls are blocked.
- Three failed attempts for one criterion block the task for user direction.
- Stale project state invalidates approval and triggers re-planning.
- Server restart reconciles running children before resuming the root task.
- Optional provider failure falls back only to an installed, locally verified compatible route.
- Missing coding, infrastructure, or deployment prerequisites produce typed proposals and never silent installation or execution.
- No failure path grants authority or leaves an unreported mutation.
- Resource exhaustion, fork bombs, runaway subprocesses, excessive model loops, oversized context/output, and repeated provider failures terminate within configured budgets and produce a blocked task rather than retrying indefinitely.
- Prompt injection from repository content or tool output is recorded as untrusted provenance and cannot modify policy, capability schemas, approval state, project scope, credentials, or environment targets.
- Concurrent project changes, model/runtime drift, adapter updates, and remote-state drift invalidate stale proposals before execution.

## Testing and acceptance

Unit and integration coverage must prove:

- Workspace tasks use `AgentRuntime` and can iteratively read, propose, obtain approval, edit, verify, and complete.
- Every effect class receives the expected policy decision.
- Mixed action batches cannot bypass per-call policy.
- Approval is exact, expiring, one-use, revision-bound, and fingerprint-bound.
- No implicit fetch occurs.
- Failed or cancelled mutations are recoverable and failed verification does not contaminate the selected branch.
- Strict structured parsing rejects prose, multiple objects, duplicate keys, path escapes, unknown fields, and oversized output.
- Restart, steer, cancel, plan revision, step revision, and undo remain durable.
- A real installed Qwen 7B model passes a disposable-project conformance scenario before it is marked broker-verified.
- Capability discovery teaches the planner every available coding operation and excludes unavailable or unauthorized operations.
- Infrastructure and deployment tests prove preview/apply separation, exact target binding, credential redaction, stale-plan rejection, post-apply verification, and separately approved rollback.
- Prompt-injection, approval-spoofing, output-escape, secret-exfiltration, concurrent-consumption, resource-exhaustion, sandbox-degradation, model-digest drift, adapter-digest drift, and audit-redaction tests exercise each trust boundary.
- The full existing suite reports all regressions, including known environment-sensitive failures separately.

## Rollout

The remediation is enabled behind a versioned `autonomous_coding` settings section. The old single-shot project workspace execution endpoint remains temporarily available only as a disabled compatibility adapter and cannot perform sensitive actions. After conformance and migration tests pass, Workspace switches to the canonical runtime by default. Existing broad broker grants are not migrated; users must create new narrow rules explicitly.
